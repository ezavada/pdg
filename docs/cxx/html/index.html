Pixel Dust Game Engine (PDG)

PDG is an open-source 2D game engine with C++ and JavaScript APIs. It provides rendering, sprites, animation, input, audio, resources, events, and optional physics. You write the application and game rules; PDG supplies the runtime systems that run them.

This is the C++ API reference for the current source tree. Start with Topics to browse by task, use the class index to find a type, or switch to the JavaScript introduction.

How an application fits together

A pdg::Port is a drawing surface. For custom graphics, respond to pdg::eventType_PortDraw and issue drawing commands through the supplied port. pdg::Attributes carries colors, gradients, strokes, text and image settings, and transforms. pdg::Drawing stores reusable elements; pdg::ElementRef provides explicit editing access. Drawing elements currently copy their Attributes.

Sprites provide managed scene objects. A Sprite belongs to a SpriteLayer, whose transform and ordering apply to its sprites. The engine handles their normal animation and drawing. Schedule motion on managed objects rather than also stepping them yourself each frame.

For example, with an existing Sprite in an active layer:

sprite.moveTo(pdg::Point(240, 180), 0.5, pdg::easeInOutQuad);
sprite.rotateBy(1.0f, 0.5, pdg::easeInOutQuad,
pdg::rotationDirection_Clockwise);

The optional MVC application framework adds controllers, views, dialogs, and controls. See src/inc/pdg/app/ and the native example test/cxx/app-control-gallery.cpp for layout, input handling, and custom controls.

Character animation

PDG supports image-frame playback and Spriter SCML animation. The Sprite pose APIs add clip sampling and seeking, blends and transitions, bone/binding transforms, procedural modifiers, two-bone IK, spring targets, contact locks, and custom Drawing artwork attached to a pose. Authored triggers are delivered through pdg::eventType_SpriteTriggerEvent. Optional Chipmunk integration supports physical animation rigs and recovery to authored animation.

The Animation topic explains the workflow and coordinate spaces. Enable pose evaluation with pdg::Sprite::enableAnimationPose() before using the pose-based extensions, and check its result: the pose adapter supports a narrower rig contract than ordinary Spriter playback.

pdg::Part currently supplies an independently animated transform, identity, hierarchy, and optional bone binding under a Sprite. Create it with pdg::Sprite::createPart(); an unbound part returns pdg::boneId_None from pdg::Part::getBoneId(). Sprite and Part expose an optional pdg::PhysicsBody through the read-only physics member; setupPhysicsBody() instantiates it explicitly. Compare sprite.physics with pdg::PhysicsBody::NoPhysics to test for absence. All absent associations point to that one shared object. Programmed movement/spin and sizing remain on Animated; mass, velocity, damping, forces and impulses belong to PhysicsBody. Sprite bodies use Chipmunk on enabled layers or PDG's basic integrator otherwise. Part bodies currently use the basic integrator; authored artwork and Part contacts/constraints remain in development.

Timing and API conventions

  • Animation durations and elapsed steps use floating-point seconds: 0.25 means a quarter second. This includes Animated motion, sprite fades, layer fades/zoom, animation helpers, and easing callbacks.
  • Angles are radians. Timed rotations accept integer rotation-direction constants; pose and Part coordinate spaces also use integer enum constants.
  • Frame numbers are integers, frame-playback rates are frames per second, and blend weights are dimensionless.
  • General timers and event timestamps retain their documented millisecond units. Convert an elapsed millisecond interval with / 1000.0 before passing it to an animation step. Animation timing lists remaining boundaries.
  • Ownership differs between value types, managed objects, and retained references. Follow each class's factory and lifetime contract, especially when keeping pose views or callback data after a callback returns.

Build and explore

The native build uses CMake and requires a C++20 compiler and standard library, including std::format. The iOS application requires iOS 16.3 or later. POSIX checkouts use ./configure and make; Windows checkouts use configure.ps1 and make.ps1. Initialize Git submodules when obtaining the source. The native control gallery is available as the CMake target pdg-app-control-gallery in a GUI build. Its source shows application initialization, event handling, controls, and custom drawing.

With the desktop JavaScript runtime built, run these examples from the repository root:

./test/demo spriter
./test/demo mvc

The animation showcase includes ordinary and blended skeleton playback, mouse aiming, a Drawing sword with spring recoil, and foot IK following a rising, sliding rock. Let the opening zoom finish; press I to toggle foot IK. The control gallery demonstrates the MVC application framework. Native regressions live in test/cxx/; script specs live in test/spec/. Run both with ./test/unit, or select a CTest suite with ./test/unit cpp:pdg-spriter-playback. ./test/rigs runs asset/controller integration checks, ./test/ui opens visual pages, ./test/tools validates test/build tooling, and ./test/perf runs benchmarks. The source checkout contains complete selection and platform instructions in test/README.md.

Runtime and build capabilities

The source tree includes desktop builds for macOS, Windows, and Linux, headless builds, an iOS integration, and an Emscripten/WebAssembly browser build. These targets do not expose identical services. Headless builds omit windowing and graphics; audio and scripting facilities depend on the target. Consult the target's build configuration when choosing an API.

CMake options include PDG_HEADLESS, USE_SPRITER, and USE_CHIPMUNK. Spriter-specific Sprite APIs require Spriter support; physical rigs additionally require Chipmunk. Query pdg::Sprite::supportsAnimationPhysics() and pdg::Sprite::isAnimationDrawingSupported() where applicable. The reference includes optional interfaces even when a particular build omits them.

API stability

Class notes describe compatibility commitments, independently of implementation quality and platform support. The same public API has the same level in both language references; language-specific wrappers may have their own rating.

Level Commitment
1 — Experimental Signatures, behavior or availability may change without a compatibility period.
2 — Evolving Implemented and supported; the contract is still settling. Compatibility is preserved where practical and breaking changes are documented in release notes.
3 — Stable Established public contract. Intentional breaking changes require an announced breaking release and migration guidance.

Methods, options, event payloads and result structures inherit their owning API's level unless separately marked. A stable Serializer/Deserializer interface does not guarantee stable snapshot bytes: supported record versions, resource policies and restoration restrictions are documented separately. Build requirements remain in force at every level; animation physics requires Chipmunk.

The application framework's views, controls, application classes and appearance classes are Level 2 — Evolving in both C++ and JavaScript. Its JavaScript guide is src/js/mvc-app/README.md; C++ declarations live under pdg/app/ and are not included in this engine reference. Unrated utilities and internal implementation types carry no new compatibility promise from this policy.

About PDG

PDG began in 2003 with Ed Zavada at Pixel Dust Games for Catan Online, continued at Dream Rock Studios, and was released under the MIT license in 2012. Its focus remains reusable 2D engine and application systems. Game-specific AI, pathfinding, rules, and content-authoring workflows belong to the application.
