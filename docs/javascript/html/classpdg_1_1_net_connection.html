Detailed Description

sends data between two network endpoints

Note
API Stability: 2 — Evolving. This API is implemented and supported, but its contract is still settling. Compatibility is preserved where practical; breaking changes are documented in release notes. See API stability.

NetConnection is part of the PDG Engine's custom protocol for games. It handles protocol negotiation. It manages communication over both a TCP connection (reliable transport with guaranteed delivery) and UDP communications (small and unreliable but fast) with the server. WebSocket and WebTransport carry the same reliable PDG framing. WebTransport additionally supplies unreliable session datagrams. The transport property identifies the underlying connection; message callbacks retain the delivery labels "tcp" (reliable) and "udp" (unreliable).

NetConnection only represents an established connection created by NetClient or NetServer.

Warning
NetClient, NetServer, and NetConnection all work together over a custom protocol. Do not attempt to use NetConnection to communicate with other kinds of servers, such as HTTP or raw TCP sockets. All you'll do is get a bunch of error messages. There are perfectly fine Net and HTTP modules built-in to Node.js (and thus to PDG) for communicating with other kinds of servers.

◆ onMessage()

NetConnection onMessage ( function callback)

set callback to handle receipt of a network message

Note
Parameter callback: NetMessageCallback.

Whenever the remote end sends a message, you will get an onMessage callback to the function specified with the message that was sent.

Parameters
callbackthe function that should be called when a message is received. The message is the first parameter passed to the callback function. Second parameter is the connection object. Third parameter is the delivery label: 'tcp' for reliable native TCP, WebSocket or WebTransport streams, and 'udp' for unreliable native UDP or WebTransport datagrams. sendDgram() uses the 'tcp' label when it falls back to reliable delivery. Inspect connection.transport for the actual transport.

◆ send() [3/4]

NetConnection send ( NetworkData message)

Send binary bytes or JSON data to the remote endpoint over TCP.

Messages use TCP and arrive in send order while the connection remains open. PDG handles packet framing.

Parameters
messageA Uint8Array (including Node Buffer), a JSON-compatible object or array, or null. See NetworkData for the complete contract.

Uint8Array inputs use binary serialization. Only the view's bytes are copied, respecting byteOffset and byteLength. The receiver gets a Node Buffer on the current Node-based networking runtimes. Plain objects, arrays and null use JSON serialization; they must be JSON-compatible and contain no circular references.

Strings, MemBlock and ISerializable instances have separate overloads. Top-level numbers and booleans are not accepted by this method.

Returns
The receiver for call chaining.

◆ sendDgram() [1/4]

NetConnection sendDgram ( ISerializable message)

send a serializable object to the remote endpoint via an available unreliable transport

The object will be sent using UDP if it is available. Delivery is not guaranteed and neither is in-order deliver of messages. This is ideal for small bits of information that are frequently resent, such as position or status updates.

NetConnection handles packet framing for you, so if the packet arrives, the NetConnection on the remote endpoint will receive an onMessage callback with the object you sent. If the message cannot be sent you will not get any notification. It will simply disappear into the ether.

Parameters
messagethe serializable object to send
Returns
itself (for call chaining)
Remarks
To guard against out-of-order delivery, you should always use a sequence number so you can drop older updates that arrive after newer ones.
See also
ISerializable
send(ISerializable)
sendDgram(NetworkData)
Warning
Any object with a serialized size greater than MTU (generally 1500 bytes, but can be smaller) will always fail to send

WebTransport uses session datagrams after handshake completion. Payloads larger than its confirmed datagram limit, disabled/unavailable datagrams, or rejected datagram writes use the reliable stream. Native UDP falls back to TCP above 1492 serialized bytes. WebSocket always uses reliable delivery. A successful datagram write still has no delivery guarantee.

◆ secure

boolean secure

Read-only indication that the carrier uses TLS.

True for wss://, false for ws:// and native TCP. Browser localAddr and remoteAddr are empty strings; localPort and remotePort are zero because browser APIs do not expose socket endpoints. Native runtimes populate the available endpoints.

◆ transport

string transport

Read-only carrier name: native or websocket.

onMessage() continues to report "tcp" for reliable messages and "udp" for native datagrams. Inspect transport to identify the carrier. WebSocket reports hasDgram as false, so sendDgram() uses send().
