Pixel Dust Game Engine (PDG)

PDG is an open-source 2D game engine with JavaScript and C++ APIs. It provides rendering, sprites, animation, input, audio, resources, events, and optional physics. You write the application and game rules; PDG supplies the runtime systems that run them.

This is the JavaScript API reference for the current source tree. Start with Topics to browse by task, use the class index to find an object, or switch to the C++ introduction.

Try the engine

The desktop pdg executable runs JavaScript using an embedded Node.js/V8 runtime. From a configured and built source checkout, run these examples at the repository root:

./test/demo spriter
./test/demo mvc

The first is the animation showcase: ordinary and blended skeleton playback, mouse aiming, a Drawing sword with spring recoil, and foot IK following a rising, sliding rock. Let the opening zoom finish, move the pointer to a character's facing side, and press I to toggle foot IK. The second is an interactive gallery of MVC views, controls, dialogs, and drawing styles.

To run your own script, use ./pdg path/to/main.js. Load the API with const pdg = require('pdg') in the desktop runtime. Use ordinary Node.js modules for services such as filesystem access, networking, and process management. PDG supplies its own graphics, event dispatch, timers, and logging.

Drawing, sprites, and events

A Port is a drawing surface. Respond to pdg.eventType_PortDraw to issue custom drawing commands through its port. Attributes carries colors, gradients, strokes, text and image settings, and transforms. Drawing stores reusable elements, and ElementRef provides explicit editing access. Drawing elements currently copy their Attributes; changing the original Attributes afterward does not update those elements.

For a managed scene, put Sprites in a SpriteLayer. Its transform and ordering apply to its sprites, and the engine handles their normal animation and drawing. Animated provides programmed movement, rotation, and size changes. For example, with an existing sprite in an active layer:

sprite.moveTo(new pdg.Point(240, 180), 0.5, pdg.easeInOutQuad);
sprite.rotateBy(Math.PI / 2, 0.5, pdg.easeInOutQuad,
pdg.rotationDirection_Clockwise);

This moves the sprite and turns it clockwise over half a second. You schedule the changes once; do not also call animate() each frame on an object that the engine already advances.

PDG events use EventEmitter and EventManager, separately from Node.js's event system. Sprite events propagate from the Sprite to its SpriteLayer and then to the EventManager until handled. See Events for event constants and payloads.

The optional MVC framework in src/js/mvc-app/ adds controllers, views, dialogs, and controls. See JavaScript application framework for imports and lifecycle, and JavaScript MVC module inventory for its separately exported classes and members. The framework README and control gallery provide further layout and input examples.

Character animation

Sprite supports image-frame playback and Spriter SCML animation. Its pose APIs add clip sampling and seeking, blends and transitions, bone/binding transforms, procedural modifiers, two-bone IK, spring targets, contact locks, and custom Drawing artwork attached to a pose. Optional Chipmunk integration supports physical animation rigs and recovery to authored animation.

Start with Sprite::enableAnimationPose() and check its result before using the pose-based extensions: their rig contract is narrower than ordinary Spriter playback. Sprite::addAnimationIK() registers a two-bone constraint; Sprite::setAnimationIKTarget() updates its target. See Animation target adapters for spring/contact helpers and Authored Spriter triggers for authored trigger notifications.

Part currently provides an independently animated transform, identity, hierarchy, and optional bone binding under a Sprite. Create it with sprite.createPart(name), rather than new pdg.Part(). getBoneId() safely returns pdg.boneId_None when unbound. Sprite and Part expose an read-only .physics property that returns pdg.PhysicsBody.NoPhysics until setupPhysicsBody() is called. Physical velocity, damping, forces and impulses belong to PhysicsBody; Animated supplies programmed movement/spin and sizing. Sprite bodies use Chipmunk on enabled layers or PDG's basic integrator otherwise. Part bodies currently use the basic integrator; Part artwork and contacts/constraints are still in development. AnimatedAttributes combines programmed transforms with eased appearance channels, without physics or automatic live updates to Drawing elements. The new body bindings are available in V8 and JavaScriptCore; browser/Wasm body bindings remain pending.

Timing and API conventions

  • Animation durations and elapsed steps use floating-point seconds: 0.25 means a quarter second. This includes Animated motion, sprite fades, layer fades/zoom, animation helpers, and easing callbacks.
  • Angles are radians. Use integer constants such as pdg.rotationDirection_Clockwise and pdg.animationSpace_World for modes and coordinate spaces. Asset, clip, bone, and part names are strings.
  • Frame numbers are integers, frame-playback rates are frames per second, and blend weights are dimensionless.
  • TimerManager delays and event timestamps retain their documented millisecond units. Convert an elapsed millisecond interval with / 1000 before passing it to animate(deltaSeconds). For authored triggers, use timeSeconds and offsetSeconds; frameTime is a compatibility millisecond field.
  • Some objects are created through factories. Follow the class's construction instructions. Copy a borrowed pose view if you need it after its callback; a JavaScript reference alone does not extend that view's validity.

Runtime and build capabilities

The source tree includes desktop builds for macOS, Windows, and Linux, headless builds and a Node.js addon, an iOS/JavaScriptCore integration, and an Emscripten/WebAssembly browser build. The browser target uses compiled engine code, and does not supply desktop Node.js services. API coverage varies between targets, particularly for newly added interfaces.

Headless builds omit windowing and graphics; audio depends on the target. Spriter animation and Chipmunk physics are optional build capabilities. Query Sprite::supportsAnimationPhysics() and Sprite::isAnimationDrawingSupported() where applicable. Seeing an API in this reference does not enable an omitted runtime feature.

Source builds use ./configure and make on POSIX, or configure.ps1 and make.ps1 on Windows; initialize Git submodules when obtaining the source. Script regressions live in test/spec/, client entry points in test/js/, and animation demo assets and instructions in test/data/animation-demo/. Run specs with ./test/unit (embedded runtime), ./test/unit --node (Node addon), ./test/unit --web (browser), or ./test/unit --ios (Simulator). ./test/rigs runs rig integration checks under Node; ./test/ui opens visual pages, ./test/tools validates test/build tooling, and ./test/perf runs benchmarks. See test/README.md in the source checkout for requirements, selection, automated runs, and artifacts.

API stability

Class notes describe compatibility commitments, independently of implementation quality and platform support. The same public API has the same level in both language references; language-specific wrappers may have their own rating.

Level Commitment
1 — Experimental Signatures, behavior or availability may change without a compatibility period.
2 — Evolving Implemented and supported; the contract is still settling. Compatibility is preserved where practical and breaking changes are documented in release notes.
3 — Stable Established public contract. Intentional breaking changes require an announced breaking release and migration guidance.

Methods, options, event payloads and result structures inherit their owning API's level unless separately marked. A stable Serializer/Deserializer interface does not guarantee stable snapshot bytes: supported record versions, resource policies and restoration restrictions are documented separately. Build requirements remain in force at every level; animation physics requires Chipmunk.

The application framework's views, controls, application classes and appearance classes are Level 2 — Evolving in both C++ and JavaScript. Its JavaScript guide is src/js/mvc-app/README.md; C++ declarations live under pdg/app/ and are not included in this engine reference. Unrated utilities and internal implementation types carry no new compatibility promise from this policy.

About PDG

PDG began in 2003 with Ed Zavada at Pixel Dust Games for Catan Online, continued at Dream Rock Studios, and was released under the MIT license in 2012. Its focus remains reusable 2D engine and application systems. Game-specific AI, pathfinding, rules, and content-authoring workflows belong to the application.

Platform requirements

The native engine requires a C++20 compiler and standard library, including std::format. The iOS application requires iOS 16.3 or later.
